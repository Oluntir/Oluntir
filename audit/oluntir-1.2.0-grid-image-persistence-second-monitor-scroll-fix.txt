Oluntir 1.2.0 – Grid image persistence and second-monitor quick-tool fix
Date: 2026-07-30

CAUSE 1 – NEW GRID IMAGE PERSISTENCE
The image selection callback first modifies the live contenteditable DOM in the GrapesJS canvas.
Project save and .oluntir backup serialize the GrapesJS component model, not that live DOM.
For components created immediately by Quick Setup, DomComponents.getComponent(editableRoot)
can temporarily return no mapping while the component View already exists. The previous fallback
then rejected the write whenever fallbackComponent.getView().el was not exactly editableRoot.
The visible image therefore remained exportable from the canvas but was absent from projectData.

IMPLEMENTATION
- Resolve the exact editable component by direct DOM mapping first.
- If that mapping is not ready, traverse the selected component, its descendants and ancestors
  and match the actual GrapesJS View element.
- Copy innerHTML before components() replaces rendered children.
- Update only the children of the exact text component; surrounding grid structure is unchanged.

CAUSE 2 – SECOND MONITOR QUICK TOOL
A later shared CSS rule reset both quick panels to height:auto/max-height:none in the popup.
That overrode the earlier bounded quick-edit layout. The quick-setup panel therefore grew beyond
its host and its Apply button could leave the visible viewport.

IMPLEMENTATION
- Bound both quick panels to the available area below the monitor title.
- Quick Setup uses a three-row grid: fixed header, scrollable body, fixed advanced area.
- The action row is sticky at the lower edge of the scrollable body.
- Existing quick-tool JavaScript and functionality remain unchanged.
